The problem I'm trying to solve in this document is how a client
can perform authenticated access to a service *without prior knowledge
about that service*, using only information available from the challenge
to bootstrap the communications.

Doing it using a pre-registered client means I have to know what client_id
to use for the service I'm talking to, so I need prior knowledge about
that service.  You could get round that if we had IVOA-federated 
client_ids, but I'm guessing that would not be easy to arrange.

So while an access method based on pre-registered client_ids is 
a reasonable way for clients to talk to an OAuth2 service,
and works for instance in astroquery where the user specifies which
service it's going to use before attempting access, I don't believe
it belongs in this document.  That may mean that services unwilling
to offer RFC7591 dynamic client registration will not be accessible
to clients that work as specified by this document,
though it doesn't mean that no OAuth2 services will be so accessible.
